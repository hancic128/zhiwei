# 定位

> 这份文档是 `docs/` 里唯一的上游文档。架构、部署、开源清单都从它推导；
> 与它冲突的功能请求，默认不做。
>
> 定稿：2026-09-19。

## 一句话

**给独立开发者与一人公司：一个人加一个 Agent，就能管住 N 台机器。**

> *For indie developers and one-person companies: one human plus one agent,
> managing N machines.*

## 目标与约束

| 项 | 内容 |
| --- | --- |
| **目标** | 技术影响力。开源不是为了变现，因此不需要为「谁会付费」做任何妥协 |
| **受众** | 独立开发者 / 一人公司（OPC），第一用户就是作者本人 |
| **架构约束** | 轻量、自托管、低成本——这是约束，不是卖点 |

**「轻量、自托管、低成本」是准入门槛，不是定位。** 这个赛道上每一个项目都这么
宣称。把它当定位，等于宣布「我和他们一样」，然后在一张对比表里比谁的镜像更小、
谁的曲线更平滑——那是稳输的比赛。

约束的作用是**否决**，不是**宣传**：它否决掉引入 K8s、Postgres、ClickHouse、
消息队列的方案，也否决掉任何「先上重型依赖以后再说」的路径。

## 第一用户：OPC / 独立开发者

**不包含「小团队」。** 这不是规模差异，是需求差异：

- OPC 的痛点：**没人帮我盯。**
- 小团队的痛点：谁能看什么、谁值班、怎么交接。

后者一进需求池，权限、多用户、审计就会一个个从后门走回来，也就是本项目一开
始想躲的那个「重」。小团队能顺手用是副产品，但**不让小团队的需求反向改架构**。

**准入判据**（新需求进来时先问这一句）：

> 这是在帮**一个人盯 N 台机器**，还是在帮**一个团队分工**？

## 三个支柱

### 1. 认知轻

「轻」有三种，前两种是红海，第三种才是空位：

| 层次 | 含义 | 状态 |
| --- | --- | --- |
| 资源轻 | 内存占用小、镜像小 | 红海，对手早三年 |
| 部署轻 | 单二进制、SQLite、5 分钟起 | 已做到，但只是入场券 |
| **认知轻** | **不用学一套仪表盘语言** | **本项目的位置** |

OPC 没有专门的人去学这套东西。他们不是「没时间看图表」，是**不想学 PromQL、
不想配 Grafana、不想维护一个仪表盘**。对他们来说，一个漂亮的 timeseries 大屏
不是资产，是负债——因为你还得盯着它。

**产品形态**：系统给的不是曲线，是**「今天要我处理的几件事」**。无事时不打扰，
有事时只有一件事要看。告警、证书到期、磁盘将满、服务探活全部收敛到同一条流。

### 2. Agent 可调用

一个人的公司里，「运维」这个角色本来就该由 agent 承担。因此数据和操作都要能
被 agent 消费与触发——**并且在设计上就把「agent 动了什么」当一等公民**，
而不是事后补日志。

注意这里绑的是**能力**，不是协议名：可被机器消费 + 受控操作 + 可审计。哪怕三
年后 MCP 不叫 MCP 了，这一条依然成立。

安全边界不变：**agent 不自主决策，人点头才动手**（见「明确不做」）。

### 3. 自托管单二进制

Rust 单二进制 + SQLite + WAL，无外部依赖，5 分钟跑起来。

这条对「技术影响力」目标还有个专门作用：**它降低别人「愿意试一次」的成本。**
别人得能真的跑起来，才有资格评判你的观点。

## 明确不做

这份清单比「做什么」更重要——它是单人项目抗过载的机制。定位清楚之后，这些
issue 可以理直气壮地拒掉。

| 不做 | 理由 |
| --- | --- |
| 用户 / 角色 / RBAC / 多租户 / SSO / LDAP | **控制台只有单一 admin token，没有「用户」这一层**（2026-09-19 定）。第一用户就是一个人，连角色都不需要 |
| 合规审计（谁看了什么） | 属于组织治理，与 OPC 无关。「agent 做了什么」是另一回事，见支柱 2 |
| HA / 集群 / 分布式存储 | 监控服务挂了对 OPC 不算灾难，不值得为它上 Postgres / ClickHouse |
| 图表拖拽 / 大屏 / 仪表盘编辑器 | 认知重的根源，直接违背支柱 1 |
| K8s 深度集成 | 第一用户跑的是 docker compose 与 systemd |
| 长周期海量指标存储 | 不做 Prometheus 替代 |
| agent 自主决策 / 自动修复 | 既是安全边界也是定位：永远是人点头才动手 |

## 影响力从哪里来

**功能会被抄，观点会被引用。** 一个十项全能的平台会被归类成「又一个 XX」然后
被忘掉；一个主张明确的小工具会被人在文章里引一句。

**事实比观点硬。** 「缓存架构该怎么取舍」这种文章人人都能写，别人可以不同意；
但「我把 monitor 部署到边缘终止 TLS 的托管平台上跑通了，节点认证不依赖客户端
证书」是无可争辩的事实。纯写字的人很多，手里有能跑起来的东西的人是少数。
**这个项目对影响力的独特价值是：它是证据，不是产品。**

由此推出一条策略：**项目线与内容线是同一个引擎。** 项目是素材和证据，博客 /
知乎 / CSDN / en.hancic.site 是放大器。不打算商业化，就更没必要把力气花在功能
完整度上，应该花在「能讲什么」上。

### 名片观点：传输层不承担身份

节点身份用 **Ed25519 请求签名**而非 mTLS 客户端证书，配合命令通道双向签名：

- 托管平台在边缘终止 TLS、不转发客户端证书 → 证书模型在 PaaS 上直接失效
  （要么容器只收明文 HTTP，要么所有节点 401）。签名模型不受影响。
- 双向闭环：ops 私钥签命令、节点验签；节点私钥签回执、monitor 验签——
  **monitor 被攻陷也伪造不出命令，传输层被攻陷也伪造不出回执。**

这是一个真实的架构判断，不是一个功能。它已经实现、已经实测、已经踩过坑
（见 `docs/DEPLOY.md` §4、`docs/DESIGN.md` D11），可以直接写成技术文章。

### 可直接出文章的素材

| 素材 | 形态 |
| --- | --- |
| 传输层不承担身份（签名替代 mTLS） | 架构判断 + 实测，最硬的一张牌 |
| 时序与快照分离：57 MB/天 → 1.6 MB/天 | 一次具体的存储取舍 |
| 单二进制 + SQLite 跑到什么规模会撑不住 | 边界诚实，反而可信 |
| 自托管生态里几乎没有像样的多机证书总览 | 场景缺口 + 自己的踩坑 |

## 与既有决策的关系

本节记录与 `docs/DESIGN.md`、Trilium「关键决策与参考」之间需要对齐的两处。
**不推翻既有决策**，只是标出张力点，待后续拍板：

1. **MCP 范围**：既有决策是「MCP 只到 read + manage，reboot / shutdown /
   kill 走 ops-server」。与支柱 2 并不冲突——操作能力可被 agent 触达，但敏感
   操作走独立通道且需人点头。要补的是**「谁在什么条件下允许 agent 触发哪一类
   操作」这层显式授权模型**，而不是放开敏感工具。
2. **用户与角色**：既有决策记的是「单组织模型，viewer / operator / admin 够用」，
   但实际实现一直是**单一 admin token**，从来没有用户表。2026-09-19 本人拍板
   **不需要用户与角色**，因此这条不再以「暂缓」而是以「不做」记入上面的排除清单：
   不做用户、角色、RBAC、SSO 中的任何一项，也不再保留相关占位界面。

## 对开源准备清单的影响

`docs/CHECKLIST.md` 的十节六十多项全是 artifacts，能把项目推到「看起来很规
范」，但推不出「别人为什么要 star」。缺的正是最上游的一节——**定位 / 受众 /
边界**。本文件补上这一节，CHECKLIST 应加一条指回这里。

另外，LICENSE 选定 Apache-2.0（干净、无 open-core 埋伏）本身已经与「企业定位」
矛盾——走企业通常要 BSL 或 open-core。**这个选择已经用行动排除了企业方向**，
与本文件一致。
