# 产品结构设计（按定位重组：扁平 + 标签）· 设计

> 日期：2026-09-19 · 状态：已定稿待落地 · 依据：[`docs/POSITIONING.md`](../../POSITIONING.md)
>
> 本文只定**结构与范围**，不含实现。落地顺序见 §10。

## 1. 背景

本人原设想的组织方式是 **应用 → 环境 → 分组 → 节点 → 容器/进程**，评估后认为过重。
本文按定位中的「认知轻」支柱（`POSITIONING.md` §三个支柱）重新定结构。

结论：**砍掉全部层级**，改为「扁平对象 + 标签」，并把默认页从总览仪表盘换成待办。

## 2. 为什么砍掉层级

不是因为它"重"，是因为**它复制的是组织架构的形状，不是一个人管几台机器时的形状**：

1. **基数对不上。** 该设计假设 N 个应用 × M 个环境 × K 个分组。实际上大部分应用
   只有一个环境、大部分分组里只有一台机器。为三台机器的场景维护四层分类法，
   成本全在用户侧。
2. **要求先录入才有价值。** 空状态必须建完应用 → 环境 → 分组才能看见东西，这是
   自托管工具流失最快的一步。做得好的都是 t=0 秒就有内容。
3. **树表达不了真实关系。** 一台机器跑多个应用、一个应用跨多台机器，这是多对多
   的图。硬塞进树里，迟早要做一次"它到底挂哪儿"的违心选择。

## 3. 结构：三层

```
注意力层（默认页）  待办
对象层（扁平列表）  节点 · 服务 · 容器 · 证书
详情层（下钻）      节点详情 · 服务详情
```

层级只在**下钻**这一个方向上存在，横向永远是平列表。

**原则：导航复制「你要做的决定」，不复制「你的机器长什么样」。**

## 4. 待办页（整套设计的支点）

它不是"告警页改了名字"，而是把多个数据源汇成一条流：

阈值告警 · 探活 down · 证书即将到期 · 磁盘将满 · 节点离线 · **平台自身异常**
（见 §8，留存清理失败属于此类）

四条设计约束：

1. **每条要带下一步。** 不是「磁盘 92%」，而是「磁盘 92%，最大的是 /var/log
   （3.2G）」并给出可执行动作。认知轻兑现在这里——把诊断结论直接摆出来，
   而不是让人自己去翻图表找原因。
2. **分组按「要不要现在动手」，不按严重级别。** 用「现在要处理 / 留意 / 已恢复」
   三档，不用 critical / warning / info。严重级别是给有值班表的人用的。
3. **允许它是空的，而且空得有底气。** 空待办 = 一句「今天没有需要处理的事」，
   下面挂一行极简状态（几台在线、几个服务健康）。这条同时解决从仪表盘切过来
   的心理落差。
4. **已恢复的留痕。** 昨晚自己好的那件事要能看见，短暂展示后折叠进「已恢复」。
   这是建立「你可以不用盯着它」这份信任的地方。

**分档的落地口径**（实施时确定，见 `crates/monitor-server/src/todo_api.rs`）：

| 来源 | 分档依据 |
| --- | --- |
| `probe`（服务探活失败） | 一律「现在要处理」——服务已经探不到了 |
| `node_offline` | 一律「现在要处理」 |
| `cert` | 看 severity——证书告警的 severity 语义本就是「过没过期」：`critical` = 已过期（HTTPS 现在就是坏的）→ 现在要处理；`warning` = 快到期 → 留意 |
| `rule`（指标规则） | 看 severity：`critical` 现在要处理，其余留意 |

**「下一步」这一条的 v1 边界**：目前是**按来源给固定指引**（探针失败怎么查、
证书怎么续、磁盘怎么清），不是按个案算出来的诊断。「找出最占地方的目录」这类
需要额外采集（目录级 disk usage）的个性化结论留到后续版本。

**节点离线的判定**：沿用与节点列表 / 概览一致的 60 秒（`NODE_OFFLINE_AFTER_MS`），
**不引入第二套阈值**。只报「曾经上报过、现在联系不上」的节点；从未上报过的
（刚入网还没跑起来）不算，否则会变成噪音。

## 5. 标签（应用与环境降级到这里）

对象（节点 / 服务 / 容器）可挂 `key=value` 标签，用途只有一个：筛选与聚合视图。
「按应用看」是用标签分组的一个**视图**，不是一层导航。

**大部分标签不需要手工建：**

| 想要的分类 | 来源 |
| --- | --- |
| 应用 | 容器自带的 `com.docker.compose.project`（已逐容器 inspect，字段在手） |
| 环境 | 一人公司通常只有一个；真有 prod/staging 也是标签 |

砍掉层级不丢信息，只是这些信息从「用户要维护的东西」变成「系统自己推出来的东西」。

**v1 只做自动标签（只读）**，手工标签往后放——YAGNI，也少一处要填的表单。

## 6. 菜单

扁平列表，不加分组标题：

```
待办 ③        ← 默认页，带未处理计数
节点
服务
容器
证书
设置
帮助
```

**落地期间这一块改过两次**，以最终形态为准：

1. 先加了「帮助」（帮助自此只在菜单里，不再出现在右下角悬浮组）；
2. 再把设置从「贴底」改回**普通列表项、排在帮助上面**——原设计写的是「设置贴底」，
   落地后本人要求取消贴底。所以现在的规则是**一条平的列表，不分组、不贴底**；
   「顶级菜单只放对象、不放对象的属性」这条原则仍然成立。

**当前状态**：7 项（概览 / 节点 / 服务 / 容器 / 证书 / 告警 / 设置，日志已在
`a359863` / `a3647dc` 收敛掉）→ **目标 6 项**。

| 现在 | 改成 | 理由 |
| --- | --- | --- |
| 概览 | **待办** | 从「给你一堆数」变成「给你要做的事」 |
| 节点 / 服务 / 容器 / 证书 | 保留，扁平 | 对象层 |
| 告警 | **降为待办的一个来源**，规则配置移进设置 | 「告警」是从数据源出发的命名 |
| 设置 | 保留（+ 告警规则） | |

**为什么不加分组标题**：7 项这个规模，分组标题是纯开销——增加行数和视觉噪音，
分类收益接近零。分组要到 15 项以上才开始有正收益。

**为什么设置贴底**：它的性质与其他项不同（其余是"对象"，它是"配置"）；且侧栏
本来就有固定贴底的控件（折叠按钮），沿用同一套视觉语言。

**概览页现有内容的去向**（该页在 `b766c06` 刚改版过，本设计覆盖其中一部分）：

| 现有内容 | 去向 |
| --- | --- |
| 5 张可点击大字卡片（节点/服务/证书/容器/告警计数） | 收敛成待办页顶部的一行状态摘要，保留可点击跳转；不再各占一张大卡 |
| 最近 5 条未解决告警 | 成为待办页主体 |
| Top N CPU / 内存节点排行 | **砍掉**。这属于典型的仪表盘内容（"给你一堆数"）；能力不丢——节点列表已支持按 CPU / 内存排序，那才是它的归宿 |
| 集群 CPU / 内存曲线 | 已在 `b766c06` 移除，维持 |

**一条长期原则**：顶级菜单只放"对象"，不放"对象的属性"。告警规则、通知渠道、
CA 身份、采集配置全是属性，进设置做二级，不新增顶级项。

**徽标**：待办显示未处理条数，为 0 时不显示（0 是噪音，且待办页会自己说"今天
没事"）。折叠成图标栏时降级为小圆点，不显示数字。

**顺序理由**：节点放在第一个对象位——它是库存的根，服务 / 容器 / 证书都挂在
节点上，是它的不同切面。

## 7. 规模定位

| 对象 | 设计中心 | 设计上限 | 超出的处理 |
| --- | --- | --- | --- |
| 节点 | 10 | 50 | 明确不保证 |
| 容器 | 150 | 1000 | 前端分页 + 筛选够用，不做虚拟滚动 |
| 服务（探针） | 20 | 100 | — |
| 证书 | 20 | 200 | 证书页已按到期升序，天然抗多 |
| 进程 | 不设 | — | 只展示 top N，不作为集合存在 |

**下限同样成立**：1 台 VPS + 0 个容器（只跑 systemd）必须可用，不能因为设计假设
「至少有几台机器组成集群」把这批用户挡在外面。

**中心点的依据是作者实况**：4 个节点（三台云主机 + 本机）、22 个容器、十几个
自托管服务、11 个域名。中心取 10 节点 = 2–3 倍余量。按自己的实况乘 2–3 倍定
中心，比按想象中的企业规模定要准。

**数量范围决定三件事，不是营销数字**：

1. **保留窗口，而不是要不要换库**——见 §8 的账。到天花板也不需要引入
   Postgres / ClickHouse：SQLite 的问题从来不是容量，是单写者并发，而 50 节点
   10 秒上报只有 5 次写/秒。
2. **前端策略**——1000 个容器用前端分页 + 筛选完全够，虚拟滚动要到万级才需要。
   列表页可沿用现在的实现。
3. **给「轻量」一条可测的红线**：**monitor 应当能在 1C1G 的机器上跑，内存占用
   目标 100 MB 以内。** 一旦为了新功能必须吃 2G 内存，就是走偏了，与定位冲突。

超出上限的：**写进 README，明确不保证**，且不做分片 / 集群 / HA。真到 5000 台
那类需求，Prometheus + Grafana 是比本项目更正确的答案。

## 8. 数据留存与降采样（本轮新增决策）

**决策：原始 10 秒数据滚动保留 14 天；之后按小时聚合长期保留。**

理由不是省磁盘，是两件事：

**一是查询成本。** 只留原始数据时，取 30 天窗口就是扫一张很大的表——设计中心下
约 260 万行，上限下约 1300 万行，会线性变慢。做小时聚合后，>14 天的查询读聚合表，
代价恒定。

**二是自动留存本身就是「认知轻」功能。** 一个会把自己用户的磁盘填满的监控工具，
是最讽刺的失败方式——而且作者本人刚被 `host.disk.usage 99.58%` 咬过。所以滚动
清理不是可选项，并且它自己也要能被观测：**留存任务失败必须出现在待办里**（已列
入 §4 的数据源）。

算账（单节点单日约 1.6 MB，为时序/快照分离后的实测值）：

| 规模 | 原始 14 天 | 小时聚合 |
| --- | --- | --- |
| 10 节点（中心） | ≈ 224 MB | 约 8.8 MB/年 |
| 50 节点（上限） | ≈ 1.1 GB（可下调到 7 天） | 约 44 MB/年 |

小时聚合几乎免费，可长期保留（建议 2 年滚动）。

**查询选源规则**：窗口 ≤ 14 天读原始 + 抽稀；> 14 天读小时表。前端时间档相应
扩到「全部 / 1 年」。

## 9. 结构层面明确不做

多级层级（应用 / 环境 / 分组）、仪表盘编辑器、自定义大屏，以及**拓扑图**。

最后一项单独列出：它是砍掉层级之后最容易冒出来的诱惑，也最重。
